# 印象问答 · 题型统一的影响评估

| 项 | 内容 |
|---|---|
| 触发 | 题库改为「每题都可多选 + 都可自定义 + 都可跳过」（见 `06-题库设计.md` v2.0） |
| 更新 | 2026-10-12 |
| 结论 | **前端已改完（原型）；后端改动量不大，但有一条统计 SQL 必须改，不改会算错。** |

---

## 1. 变更摘要

| 变更 | 影响面 |
|---|---|
| 单选 → 多选 | 统计口径（占比之和不再等于 100%） |
| 新增「自定义答案」 | 提交接口结构、`answer.text_content` 语义、统计接口、结果页 |
| 全部可跳过 | **占比分母**（这是最容易算错的地方）、样本量按题计算 |
| 题型三合一 | `question.type` / `required` 字段语义弱化 |

---

## 2. 对数据库的影响

### 2.1 不用改的（现有设计已经支持）

- **`answer` + `answer_option` 的两层结构天然支持这个变更**：`answer` 一行代表"某人对某题的作答"，`answer_option` 若干行代表"选中了哪些选项"，`answer.text_content` 存文本。
- 一题同时有**选项 + 自定义文本** → 同一 `answer.id` 下既有 `answer_option` 行、又有 `text_content`。**结构上完全成立，无需改表结构。**
- 纯自由题（无预设选项）→ `answer` 有 `text_content`，没有 `answer_option` 行。也成立。

> 这是原设计"比需求更通用"带来的红利：当初把文本和选项拆成两张表，现在不用动结构。**面试里可以说：这个变更没有产生任何表结构改动，只改了字段语义和统计口径。**

### 2.2 必须改的：字段语义（否则注释会误导后来的人）

```sql
-- question 表：三处语义修正
ALTER TABLE question
  MODIFY COLUMN type        TINYINT  NOT NULL DEFAULT 1
    COMMENT '展示类型：1=有预设选项，2=纯自由填写（不再是单选/多选/开放）',
  MODIFY COLUMN max_choices TINYINT  NOT NULL DEFAULT 0
    COMMENT '最多可选数：0=不限（注意与旧语义不同，旧默认值是 1）',
  MODIFY COLUMN max_length  SMALLINT NOT NULL DEFAULT 200
    COMMENT '自定义答案字数上限；0=不允许自定义';

-- answer 表：这条注释现在是错的，必须改
ALTER TABLE answer
  MODIFY COLUMN text_content VARCHAR(200) NULL
    COMMENT '自由/自定义答案文本（任何题型都可能填，不再限于开放题）；未填为 NULL';
```

### 2.3 需要决策的：`question.required` 怎么处理

新模型下"可跳过"是**全局规则**，逐题的 `required` 变得没有意义。两个选项：

- **A（推荐）**：保留字段但恒为 `0`，注释标注「v2.0 起全部可跳过，本字段仅供将来恢复差异化设置」。
- **B**：重命名为 `allow_skip TINYINT(1) NOT NULL DEFAULT 1`（语义反转，更直观，但要改代码里所有引用）。

### 2.4 一个无法用约束表达、只能靠 Service 保证的规则

「`answer` 行至少要有一个选项或一段文本」——这条**跨表规则写不进 CHECK 约束**（因为要判断是否存在 `answer_option` 子行）。处理方式：

- **Service 层在同一事务内保证**：`keys` 与 `custom` 都为空时，**不插入 `answer` 行**。
- 这样"跳过"在数据库里就是"没有这一行"，统计时天然不算作答，不需要额外的 `is_skipped` 标记。

这是可以写进面试的取舍：**用"不写入"表达"跳过"，避免引入冗余状态字段。**

## 3. 对 API 的影响

### 3.1 提交接口 payload（`04-API接口清单.md` P-03）

```jsonc
{
  "submitToken": "8f1c2c7e-2a44-4a2e-9c1b-7d3f9c0b1a55",
  "durationMs": 96000,
  "answers": [
    { "questionId": 1, "optionIds": [11, 13], "text": null },        // 只勾选项
    { "questionId": 2, "optionIds": [],       "text": "话不多但很稳" }, // 只自己写
    { "questionId": 3, "optionIds": [21],     "text": "补充：你记性很好" } // 两者都有
    // 跳过的题：前端直接不上传
  ]
}
```

**校验规则（与旧版的关键差异，旧版是"选择题必填 optionIds / 开放题必填 text"）：**

1. `answers` 至少 1 条非空项 —— 对应全局提交下限（`minRequiredAnswers`，原型设为 1）。
2. 单条内 `optionIds` 与 `text` **至少一个非空**，否则该条视为无效（建议直接忽略该条，不报错）。
3. `optionIds` 每项必须属于该 `questionId`（防 IDOR 伪造）；长度 ≤ `question.max_choices`（**0 表示不限**）。
4. `text` 长度 ≤ `question.max_length`；存库前做 XSS 转义（或输出时转义）。
5. 跳过的题**可以不上传**，后端不必要求"题数与题目数一致"。

### 3.2 统计接口需要扩容

现有的 `GET .../open-answers?questionId=9` 是按"只有开放题才有文本"设计的，**现在任何题都可能有文本**，所以：

- 该接口的语义应泛化为「取任意题的自由文本回答」，`questionId` 不再限定开放题。
- 统计响应里，每题要返回**两个独立的块**，不能混算：

```jsonc
{
  "questionId": 1,
  "answeredCount": 14,          // ← 本题回答人数，是下面 percent 的分母
  "optionStats": [
    { "optionId": 11, "content": "靠谱", "votes": 9, "percent": 64.3 }
  ],
  "customAnswers": [            // 自定义答案单独一块，不参与选项百分比
    { "answerId": 101, "text": "挺靠谱的一个人" }
  ],
  "skippedCount": 3             // 跳过本题的人数
}
```

## 4. 对统计 SQL 的影响（**不改就是错的**）

### 4.1 潜在错误：占比分母

旧版所有题都必答，所以「选项票数 ÷ 总提交数」是对的。**现在题目可以跳过，这两个数不相等**，必须把分母换成"回答了本题的人数"。

```sql
-- ✅ 修正后的选项分布
SELECT
  o.id            AS option_id,
  o.content,
  COUNT(ao.id)    AS votes,
  ROUND(
    COUNT(ao.id) * 100.0
    / NULLIF((SELECT COUNT(*) FROM answer WHERE question_id = o.question_id), 0)
  , 1)            AS percent
FROM question_option o
LEFT JOIN answer_option ao ON ao.option_id = o.id
WHERE o.question_id = ?
GROUP BY o.id, o.content
ORDER BY o.sort_order;
```

> `NULLIF(..., 0)` 防止无人作答时除零。**这是本次变更里唯一会导致结果出错的点**，其余都是展示层的调整。

### 4.2 每题样本量（结果页的强制要求）

不再只报一个"共收到 N 份回答"，而是逐题报：

```sql
SELECT q.id, q.title, COUNT(a.id) AS answered_count
FROM question q
LEFT JOIN answer a ON a.question_id = q.id
WHERE q.questionnaire_id = ?
GROUP BY q.id, q.title
ORDER BY q.sort_order;
```

### 4.3 自定义答案列表

```sql
SELECT a.id, a.text_content, a.created_at
FROM answer a
WHERE a.question_id = ?
  AND a.text_content IS NOT NULL AND a.text_content <> ''
ORDER BY a.created_at DESC
LIMIT ? OFFSET ?;
```

## 5. 对结果页的影响

每题卡片必须拆成**四块**，且视觉上明确区分"统计"与"原文"：

| 区块 | 内容 | 关键约束 |
|---|---|---|
| 样本量 | 「本题 14 人回答，3 人跳过」 | 逐题显示；< 3 人时按 PRD §4.2 不下结论 |
| 选项分布 | 选项 + 票数 + 占比 | 分母 = 14；占比之和会 > 100%，文案要写"被提到的比例" |
| 自定义答案 | 原文列表 | **不合并进百分比**，单独一块展示 |
| 跳过人数 | 「3 人跳过了这题」 | 跳过率高本身就是有效信息（说明这题没问到点上） |

---

## 6. 需要拍板的三个点

1. **多选要不要留上限？** 现在全部是"不限"。第 1 题有 9 个选项，不限量时可能有人全选，会让分布失去区分度。建议至少给 9 选项那题设 `maxSelect: 3~4`。
2. **提交下限设几？** 当前"至少答 1 题"。若想要更实的数据，建议提到 **3**（`CONFIG.minRequiredAnswers = 3`）。
3. **`question.type` / `required` 字段怎么处理？** 见 §2.3 的 A / B 方案。

## 7. 改动成本小结

| 层 | 改动量 | 状态 |
|---|---|---|
| 前端原型 | 逻辑重写（题型统一、自定义输入、跳过） | ✅ 已完成并通过测试 |
| 数据库表结构 | **零改动** | 只需改注释（§2.2） |
| 数据库字段语义 | 3 个字段（`max_choices` 默认值、`max_length` 适用范围、`text_content` 适用范围） | 待做 |
| 统计 SQL | 1 处分母修正（**必须**）+ 2 处新增查询 | 待做 |
| API 契约 | 提交 payload 校验规则、统计响应结构、open-answers 接口泛化 | 待做 |
| 结果页 | 每题拆成四块展示 | 待做 |

**核心结论**：这不是一次伤筋动骨的改动。真正会出问题的只有一处——**统计占比的分母**。其余都是"注释与展示"层面的调整。
